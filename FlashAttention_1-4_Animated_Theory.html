FlashAttention 1–4

Same attention problem. Smarter data movement and execution.

AudienceDevelopers and ML engineers who know basic neural networks, matrix multiplication and Transformer attention
DeliveryConversational, technically careful, paced for live explanation
Toy example16 tokens · head dimension 8 · K/V tile size 4
THEORY

This guide presents the core idea behind FlashAttention: exact dense attention can be reorganized to reduce data movement and avoid storing the full attention matrix in high-bandwidth memory (HBM).

How to use this theory guide
  • Use each THEORY section to understand the concept shown in the adjacent animation.
  • Use the BOARD material as a compact reference for the equations and definitions.
  • Pause at the marked checkpoints. Let the audience think before you reveal the answer.
  • The toy example uses 16 tokens, head dimension 8, and a key/value tile size of 4. Keep those numbers consistent throughout the derivation.
  • The benchmark section leaves performance values to be filled from a real GPU run; crossover points depend on the tested setup.
Important technical framing

FlashAttention is an exact-attention algorithm in the algorithmic sense: it does not approximate attention by dropping tokens, using low-rank factors, or replacing the attention rule. However, GPU implementations use finite-precision arithmetic, and options such as FP8 or polynomial exponential approximations introduce numerical differences. Do not promise bit-for-bit equality with every conventional implementation.

The full-attention arithmetic still scales quadratically with sequence length. FlashAttention primarily changes the I/O behaviour and intermediate-memory footprint, not the fundamental amount of pairwise attention work. Also, PyTorch's scaled dot-product attention chooses among several eligible backends; it does not guarantee that the FlashAttention backend is selected for every input.

Part 4

Standard attention: follow the intermediate matrices

about 6–7 minutes
THEORY

For one attention head, scores are computed as QKᵀ/√d, probabilities are softmax of those scores, and the output is the probability matrix multiplied by V. The score and probability matrices can each have N×N elements.

WRITE ON THE BOARD

Write the standard attention equations:

\[S = \frac{QK^T}{\sqrt{d}}\]
\[P = \operatorname{softmax}(S) \quad \text{(row-wise)}\]
\[O = PV\]

Add the shapes:

Q: N × d       Kᵀ: d × N       S: N × N
P: N × N       V: N × d       O: N × d

write S:  N × N
read  S:  N × N
write P:  N × N
read  P:  N × N

Then calculate:

N = 4096, 2 bytes / element
4096 × 4096 × 2 = 32 MiB per N × N matrix

Illustrative materialised path:
S write + S read + P write + P read
= 4 × 32 MiB = 128 MiB
per head, per layer (excluding Q/K/V/O)

Box this question:

Can we compute O without writing S and P to HBM?
THEORY audience pause

The full score and probability matrices are temporary intermediates. The final output can be computed without materializing them in HBM by processing score tiles and maintaining a compact softmax state.

Part 5

The central idea: tiling and fusion

about 4–5 minutes
THEORY

Tiling divides the query, key, and value matrices into blocks. Fusion combines score computation, softmax updates, and value accumulation so intermediate tiles can be consumed on chip.

WRITE ON THE BOARD
FLASHATTENTION CORE IDEA

1. Split Q, K, V into tiles.
2. Move only the required tiles into fast on-chip memory.
3. Compute score tiles and consume them immediately.
4. Maintain running softmax statistics and output accumulators.
5. Write the final O tile to HBM.

Full N × N S and P are not materialised in HBM.

Draw:

HBM:       Q     K     V
            \    |    /

              \ | /
               v
          ON-CHIP WORKSPACE
       Q tile + K tile + V tile
         score → softmax update
            → output accumulator
               |
               v
HBM:       final O tile
Part 6

Build the baseline with one query

about 6–7 minutes
THEORY

A single query row provides a simple derivation: compute its scores against keys, normalize them with softmax, then use the probabilities to form a weighted sum of values.

WRITE ON THE BOARD

Draw three 16-by-8 grids:

Q (16 × 8)       K (16 × 8)       V (16 × 8)
q1               K1               V1
q2               K2               V2
...              ...              ...
q16              K16              V16

Underneath, write:

\[s_i = \frac{q_1 \cdot k_i}{\sqrt{d}}, \qquad i=1,\ldots,16\]
\[w_i = \frac{e^{s_i}}{\sum_{j=1}^{16}e^{s_j}}\]
\[O_1 = \sum_{i=1}^{16} w_i V_i \qquad \text{shape: } (1\times16)(16\times8)=1\times8\]

Add a small note:

\[\text{For numerical stability: subtract the row maximum before exponentiation.}\]
THEORY transition

Softmax normalizes each score by the sum of exponentials across every key. Computing a separate softmax for each tile changes the denominator and therefore does not reproduce full attention.

Online softmax: the mathematical heart of FlashAttention

about 14–17 minutes

7.1 Split the keys and values into tiles

THEORY

Partition the keys and values into tiles. Each tile contributes exponentiated scores to a shared normalization denominator and contributes a correspondingly weighted sum of values.

Tile 1: K1–K4       V1–V4
Tile 2: K5–K8       V5–V8
Tile 3: K9–K12      V9–V12

q1 × K9:K12    → [s9  s10 s11 s12]

7.2 Why independently normalising every tile is wrong

THEORY

Independent tile outputs cannot simply be averaged or concatenated. Their local denominators differ, so each tile must be rescaled to a common normalization before the partial results are combined.

WRITE ON THE BOARD

Write:

\[\text{Tile output} = \frac{\text{tile numerator}}{\text{tile denominator}}\]

Then:

Do NOT do this:
O = O_tile1 + O_tile2 + O_tile3 + O_tile4

Cross it out and write:

Keep each tile's numerator and denominator.
Combine first. Divide once at the end.

7.3 The simple online-softmax idea before numerical stability

THEORY

For a tile, let l be the sum of its exponentiated scores and u the weighted sum of its value vectors. When a later tile arrives, rescale the previous l and u to the new score range, then add the new tile contribution.

WRITE ON THE BOARD
\[L_j = \sum_{i\in\text{tile }j}e^{s_i}\]
\[U_j = \sum_{i\in\text{tile }j}e^{s_i}V_i\]
\[O_j = U_j/L_j\]

Then accumulate:

\[U = U_1+U_2+U_3+U_4\]
\[L = L_1+L_2+L_3+L_4\]
\[O_1 = U/L\]

Circle U and L.

7.4 Prove it with four numbers

THEORY

A small numerical example makes the rescaling visible: if two tiles have total exponential weights 4 and 6 and weighted-value sums 20 and 90, the combined result is (20 + 90)/(4 + 6) = 11. The tile outputs must be combined by their weights.

WRITE ON THE BOARD
Tile 1 Tile 2 Combined
Exponentials 1, 2 3, 4 1, 2, 3, 4
Values 10, 20 30, 40 10, 20, 30, 40
Denominator 3 7 3 + 7 = 10
Numerator 50 250 50 + 250 = 300
Local output 16.7 35.7 Do not average
Final result 300 / 10 = 30

7.5 Add the running maximum for numerical stability

THEORY

Subtracting the maximum score before exponentiation prevents overflow and improves numerical stability. Track the running maximum m, denominator l, and weighted numerator u; when m increases, rescale the earlier l and u by exp(old_m − new_m).

WRITE ON THE BOARD

Define the score tile S_j for one query row. Write:

\[m_{new}=\max\left(m_{old},\ \max(S_j)\right)\]
\[\alpha=e^{m_{old}-m_{new}}\]
\[P_j=e^{S_j-m_{new}}\]
\[l_{new}=\alpha l_{old}+\operatorname{rowsum}(P_j)\]
\[u_{new}=\alpha u_{old}+P_jV_j\]

Final output:

\[O=\frac{u_{new}}{l_{new}}\]

Initialise each row with:

m = -∞,   l = 0,   u = 0

Add a box:

Carried between key/value tiles:
(m, l, u) — small row-wise state

7.6 Extend from one query to a query tile

THEORY

The same recurrence applies to a block of query rows. Each row keeps its own running maximum, denominator, and output accumulator while key/value tiles are streamed through the block.

WRITE ON THE BOARD
Query tile 1  ── process all K/V tiles ──> output rows 1–4
Query tile 2  ── process all K/V tiles ──> output rows 5–8
Query tile 3  ── process all K/V tiles ──> output rows 9–12
Query tile 4  ── process all K/V tiles ──> output rows 13–16

Final O: 16 × 8, written to HBM
Full S:  16 × 16, never materialised in HBM
Full P:  16 × 16, never materialised in HBM
THEORY checkpoint

The central online-softmax state is (m, l, u). It is sufficient to combine tiles exactly in real arithmetic and to recover each output row as u/l, subject to normal floating-point rounding.

Part 8

Why tiling reduces HBM traffic

about 6–8 minutes
THEORY

Tiling reduces HBM traffic because a query block and key/value tile are loaded and reused for matrix products before being evicted. The algorithm avoids writing and rereading the N×N score and probability matrices.

WRITE ON THE BOARD

Define B_r as the number of query rows in one query tile:

\[\text{Number of query tiles}\approx\frac{N}{B_r}\]

Simplified capacity relationship:

\[B_r=O\left(\frac{M}{d}\right)\]

Therefore:

\[\text{K/V reads}\approx O(Nd)\times O\left(\frac{Nd}{M}\right) =O\left(\frac{N^2d^2}{M}\right)\]

Total simplified I/O:

\[\text{FlashAttention I/O}=O\left(Nd+\frac{N^2d^2}{M}\right)\]

Compare:

\[\text{Materialised attention I/O}=O(Nd+N^2)\]

Add a prominent note:

Important: I/O complexity improves.
Dense-attention arithmetic is still quadratic in N.
THEORY recap

FlashAttention 1 introduced an IO-aware exact-attention algorithm built from tiling, online softmax, and fused operations. Its main gain comes from reducing intermediate-memory traffic, not from reducing dense attention’s quadratic arithmetic count.

Part 9

FlashAttention 1 versus FlashAttention 2: better parallelism

about 8–9 minutes
THEORY

FlashAttention 2 reorganized work to expose more parallelism and improve GPU utilization. Its changes include partitioning work across query blocks, adjusting warp responsibilities, and reducing non-matrix operations.

THEORY continued

When query rows are divided into independent blocks, each block can compute its output separately. This provides parallel work across a sequence and avoids unnecessary coordination between blocks.

THEORY continued

Splitting work across key blocks can help when query parallelism is insufficient, but partial softmax states then need to be combined. The online-softmax recurrence provides a mathematically consistent merge.

WRITE ON THE BOARD
FA1 — simplified loop organisation
for each K/V tile:          # outer loop
    for each Q tile:        # inner loop
        update output state

FA2 — simplified loop organisation
for each Q tile:            # outer loop
    for each K/V tile:      # inner loop
        update this Q tile's output state

             Key / Value tiles
             KV1   KV2   KV3   KV4
Query Q1      ×     ×     ×     ×
blocks Q2     ×     ×     ×     ×
       Q3     ×     ×     ×     ×
       Q4     ×     ×     ×     ×

Label FA1 KV tiles outer and FA2 Q tiles outer.

FA1: remove full N × N HBM intermediates
FA2: expose more independent Q-block work; improve warp partitioning

The useful parallelization strategy depends on workload shape and hardware occupancy. More parallel tasks help only when there is not already enough independent work and when coordination costs remain manageable.

Part 10

FlashAttention 3: overlap the work on Hopper

about 9–11 minutes
THEORY

FlashAttention 3 targets Hopper GPUs by overlapping data movement, matrix multiplication, and softmax work. Its pipeline aims to keep specialized hardware units busy instead of waiting for each operation to finish before starting the next.

THEORY continued

FP8 reduces data size and can increase throughput on supported hardware, but it changes numerical precision. Scaling, accumulation precision, and the input distribution affect accuracy and must be evaluated for the intended workload.

THEORY continued

FlashAttention 3 retains tiled attention and online softmax while adapting the schedule to Hopper features such as asynchronous transfers and warp specialization. The architectural schedule is the key change.

THEORY precision caveat

Algorithmically, FlashAttention computes dense attention without dropping tokens. Floating-point formats and approximations can still produce small numerical differences, so bitwise equality with another implementation is not guaranteed.

Part 11

FlashAttention 4: Blackwell changes the bottleneck again

about 11–13 minutes
THEORY

FlashAttention 4 is designed around Blackwell’s changed performance balance. As matrix multiplication accelerates, exponentials, memory movement, and synchronization can become more visible bottlenecks.

THEORY continued

Tensor Memory (TMEM) provides an on-chip destination for tensor-core results on Blackwell. Managing these results and their movement through the kernel is part of the new schedule.

THEORY continued

Fast matrix multiplication can make exponential evaluation a limiting stage. FlashAttention 4 uses a software-assisted exponential method designed to reduce this bottleneck while controlling numerical error.

THEORY continued

Online softmax rescales accumulators when a larger score maximum appears. Conditional rescaling can avoid some unnecessary rescale work while preserving the required normalization logic.

THEORY continued

Two-CTA matrix multiplication lets a pair of thread blocks cooperate on a tile. In the backward pass, this can improve work distribution and reduce the cost of certain reductions.

THEORY continued

FlashAttention 4 uses CuTe-DSL to express low-level GPU operations and schedules. The implementation language helps map the algorithm onto Blackwell hardware; it does not change the attention definition.

WRITE ON THE BOARD

Start with a simplified comparison:

BF16 tensor-core throughput 4,096 ops / clock / SM 8,192 ops / clock / SM
Exponential throughput 16 ops / clock / SM 16 ops / clock / SM
Shared-memory read 128 B / clock / SM 128 B / clock / SM
Tensor-core accumulator storage Registers TMEM, 256 KB / SM

The bottleneck moved.

THEORY summary of FA4

FlashAttention 4 responds to Blackwell’s bottlenecks with a hardware-specific schedule involving TMEM, pipelining, efficient exponentials, softmax rescaling, and cooperative matrix multiplication.

import torch
import torch.nn.functional as F
from torch.nn.attention import sdpa_kernel, SDPBackend

def naive_attention(q, k, v, causal=False):
    scale = q.shape[-1] ** -0.5
    s = (q @ k.transpose(-2, -1)) * scale          # N x N scores (materialised)
    if causal:
        n = s.shape[-1]
        future = torch.ones(n, n, dtype=torch.bool, device=s.device).triu(1)
        s = s.masked_fill(future, float("-inf"))
    p = torch.softmax(s, dim=-1)                   # N x N probabilities (materialised)
    return p @ v

def flash_attention(q, k, v, causal=False):
    # Require the FlashAttention backend: errors if these inputs are not eligible
    with sdpa_kernel(SDPBackend.FLASH_ATTENTION):
        return F.scaled_dot_product_attention(q, k, v, is_causal=causal)

def median_ms(fn, q, k, v, warmup=10, iters=50):
    for _ in range(warmup):
        fn(q, k, v)
    torch.cuda.synchronize()
    times = []
    for _ in range(iters):
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        fn(q, k, v)
        end.record()
        torch.cuda.synchronize()
        times.append(start.elapsed_time(end))
    times.sort()
    return times[len(times) // 2]

def peak_mb(fn, q, k, v):
    torch.cuda.synchronize()
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()
    base = torch.cuda.memory_allocated()
    fn(q, k, v)
    torch.cuda.synchronize()
    return (torch.cuda.max_memory_allocated() - base) / 2**20   # allocated, NOT HBM traffic

B, H, D, dtype = 1, 16, 128, torch.bfloat16
print("seq_len,naive_ms,flash_ms,naive_mb,flash_mb")
for N in [512, 1024, 2048, 4096, 8192]:
    q, k, v = (torch.randn(B, H, N, D, device="cuda", dtype=dtype) for _ in range(3))
    torch.testing.assert_close(naive_attention(q, k, v), flash_attention(q, k, v),
                               atol=2e-2, rtol=2e-2)          # same attention, up to rounding
    t_naive, t_flash = median_ms(naive_attention, q, k, v), median_ms(flash_attention, q, k, v)
    m_naive, m_flash = peak_mb(naive_attention, q, k, v), peak_mb(flash_attention, q, k, v)
    print(f"{N},{t_naive:.3f},{t_flash:.3f},{m_naive:.1f},{m_flash:.1f}")

12.3 What this means in practice

THEORY

FlashAttention can reduce attention memory use and improve throughput in training and prompt prefill, but end-to-end benefit depends on the model, sequence lengths, batch size, and the rest of the system.

WRITE ON THE BOARD
What FlashAttention can improve:
✓ Avoid materialising full N × N score/probability matrices in HBM
✓ Reduce attention intermediate-memory pressure
✓ Reduce HBM I/O for suitable workloads
✓ Improve prefill and training performance on supported shapes

What it does NOT automatically do:
✗ Make dense attention linear-time in N
✗ Remove the KV cache
✗ Guarantee a speedup for every sequence length and batch size
✗ Guarantee PyTorch SDPA always selects the Flash backend

12.4 Decode and Flash-Decoding

THEORY

During autoregressive decode, a new query may attend to a long key/value cache. Splitting the cache across workers creates parallel tasks; each worker computes a partial online-softmax state, and those states are merged before producing the output.

WRITE ON THE BOARD
PREFILL:
Many query rows → split work across query blocks

DECODE:
One/few query rows + long KV cache
→ split KV cache into chunks
→ compute partial (m, l, u)
→ merge partial states
→ final output

Notes

Recording notes and technical checks

1. Claims to phrase carefully

  • Say "same mathematical attention, up to floating-point effects", not "bit-for-bit identical". Different operation ordering, data types, and approximations can change low-order bits.
  • Say "avoids materialising the full N×N score and probability matrices in HBM", not "the N×N matrix never exists anywhere". Score tiles exist temporarily on chip.
  • Say "reduces I/O and intermediate-memory requirements", not "turns attention into linear-time attention". Dense full attention still has quadratic pairwise arithmetic in sequence length.
  • Treat M/d as a simplified scaling relationship for tile capacity, not a production tile-size formula. Actual tile dimensions are hardware- and kernel-dependent.
  • Keep H100's 228 KB maximum shared-memory capacity distinct from its 256 KB combined L1/shared-memory structure.
  • Do not say PyTorch SDPA always selects FlashAttention. The backend is selected automatically from the implementations eligible for the current inputs and device.
  • Report benchmark values from the run shown on screen. Don't use a fixed 500–1,000-token crossover or a universal speedup unless your own measured configuration supports it.
  • Describe FP8 and polynomial exponentials as lower-precision / approximate numerical paths, not as bit-exact computations.
